# Issue #40 D2c｜共通エピソード・年次確定・型付き履歴（検証モデル）

- 設計：[D0](issue40-history-generation-d0.md)§3・§4.1・§8・§9・§12 D2c（停止線：活動中と終了、再発・失敗・出典・未来遮断・重複防止。現行本番回帰）
- 前工程：[D2b](issue40-d2b-design.md)（完了）
- 状態：**実装済み。70世界の試走結果は§6**。本番の新規世界・進行・選択・保存は置き換えていない。

## 1. 範囲

D2cは、4系統（D3a食料・D3b交易・D3c災害復旧・D3d社会変容）が共通に使う枠組みだけを作る。系統ごとの発生・対応・終結の条件と、その効果はD3で決める。

- 枠組みを実世界で動かすため、最小の**検証用プローブ**（`probe-d2c`、食料の不足の記録を追うだけ）を置いた。プローブは食料系統ではない。D3aで食料系統の定義に置き換える。
- エピソードは文明に何も書き込まない（効果なし、乱数なし）。D3の効果は、系統ごとの行動の候補として別に加える。エピソードに人口・食料・交易・建物の状態を複製しない（D0 §3）。

## 2. 設計

### 2.1 型付き履歴（`src/story/episode-d2c-review.ts`）

- 正本は、遷移を追記するだけの列（`EpisodeStore.transitions`）。D0 §4.1の型に合わせた。
  - 遷移の種類：started／reassessed／response-started／response-failed／response-changed／resolved／abandoned
  - 各遷移が持つもの：ID（`<エピソードID>/<番号>`）、年、同じ年の中の順序（seq）、根拠（`EvidenceRef`）、系統固有の状態（`state`。JSONの値のみ）
  - 失敗・方針変更・断念には理由（`reason`）が必須。開始には、親のエピソード（`parentEpisodeId`）を付けられる。
- 根拠の型：既存の記録ID（`record`）、台帳のキーと確定年（`ledger`）、他のエピソード（`episode`）。
- 活動中のエピソードの索引（`active`）は、遷移から再構築できる。`checkEpisodeHistory`が全体を再構築し、保持している索引と一致しなければ拒否する。
  - 系統固有の状態は、最後の遷移の`state`。変化しない年には何も保存しない。
  - そのため定義は、遷移の間の年ごとのカウンターを持たない。継続年数などは確定した台帳から読む。
- 観測：`episodesAt(s, year)`は、その年までの遷移だけから組み立てる。後の年が過去の観測を変えることはない。確定した年より後は読めない。

### 2.2 年次確定（D0 §8）

- `finishYear`の最後、その年の台帳を確定した直後（`commitObservation`の後）に、`commitEpisodeYear`を一度だけ呼ぶ。
  - その年の記録・経済・台帳は、この時点で確定している。
- 選択待ちの年は`finishYear`まで進まないので、エピソードは確定しない。選んだときに一度だけ確定する。選択待ちで保存した世界は、エピソードを前年まで確定している。
- 確定の検査：
  - 台帳の確定前には呼べない。
  - 同じ年を二度、または年を飛ばして確定することはできない（`committedThrough`）。
  - 他の定義セットのエピソードは続けられない。
- 新しく生じた課題が影響するのは翌年以降（D0 §8.6）。D2cでは影響そのものを持たない。

### 2.3 規則（停止線）

| 規則 | 実装 |
|---|---|
| 系統ごとに活動中は最大1つ、4系統は並行できる | 定義は系統ごとに1つ。活動中なら`advance`、なければ`start`だけを呼ぶ |
| 再発は新しいID | ID＝`<系統>-<開始年>`。同じ年に終わって始まることはない（1年に1系統あたり遷移は1つ） |
| 1年に1エピソードあたり遷移は1つ、終了後は遷移しない | 遷移の検査（同じ年の2件目・終了後の遷移を拒否） |
| 失敗・方針変更は対応中だけ | response-failed／response-changedは`response==='running'`のときだけ |
| 出典が実在し、未来の年でない | 記録はIDから引けて、年が遷移の年以下。台帳は確定年が遷移の年以下。エピソードは既存で、自分自身ではない |
| 開始は記録から | startedには記録の根拠が1件以上必要 |
| 同じ起点で二度始めない | 一度エピソードを始めた記録は、同じ系統で再び起点にできない |
| 親は既存の、それ以前のエピソード | 開始の検査 |
| 状態はJSONの値だけ | 関数・非有限数・プロトタイプ付きのオブジェクトを拒否（試験で、関数が黙って落ちる不備を見つけて直した） |

### 2.4 検証用の方針と保存

- `createEventPolicyD2a(…,{decisions:true,episodes:EPISODE_PROBE_D2C})`。方針のキーは`…:hardship-linked+decisions-d2b+episodes:probe-d2c`。
  - 検証用の世界は、0年からこの方針で進めたときだけ続けられる（D2aのまま）。
- 検証用の保存（D2bの形式）に、方針`hardship-linked+decisions-d2b+episodes-probe-d2c`を加えた。
  - エピソードは状態の一部として歴史のハッシュに含まれる。
  - 保存時・読込時に`checkEpisodeHistory`で検査する。

### 2.5 プローブ（`src/story/episode-probe-d2c-review.ts`）

- started：その年に、経済が地区の不足を記録した（不足が3年続くと記録される）。
- reassessed：活動中に、別の地区の不足が記録された。
- resolved：すべての地区で、直近5年の充足率が0.90以上（経済が保持する5年分）。
- 対応・失敗・断念はしない（それらは枠組みの試験で、台本どおりに動く定義を使って確かめる）。

### 2.6 実装と本番への影響

| ファイル | 変更 |

| `src/story/episode-d2c-review.ts`（新規） | 型・定義セット・年次確定・全体の検査・観測 |

## 3. テスト（`tests/episode-d2c.test.mjs`、5件）

- 一連の経過：開始→対応→失敗（理由つき）→再試行→方針変更→断念、その後の再発は新しいIDで親を参照する。履歴の検査、過去の観測、確定年より後の読取の拒否。
- 並行と確定：4系統が同じ年に並行し、seqが付く。同じ年の二度目の確定、台帳の確定前、他の定義セット、同じ系統の重複定義、自作の定義セットを拒否する。
- 根拠：空、存在しない記録、未来の年の台帳、未知の親、JSONでない状態、対応していない失敗、理由のない断念、同じ起点での再開始、自分自身の参照を拒否する。未来の年の記録は、確定時にはまだ存在しないので引けない。
- 改ざん：遷移の重複・欠落・年の変更・索引の改変・根拠の差し替え・確定年の変更・順序の逆転を、全体の検査が拒否する。枠組みは`episodes`以外を書き換えない。
- 実世界（1200年）：エピソードなしの世界と、文明・建築台帳が一致する。過去の観測は後で読んでも同じ。エピソードが活動中の選択待ちで保存→読込→選択→120年で、直接進めた世界と一致する。
