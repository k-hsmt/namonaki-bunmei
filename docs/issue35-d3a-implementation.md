## 1. やったこと

### 1.1 v8の年次処理に、記録に入らない受け口を通した

v8の年次処理の本体には、本番の経路で使う専用の受け口（収穫と廃棄を受け取り、v8の記録に入れる）と、既存の公開の受け口（`EconomyObserver`）を**同時には使えない**決まりがある。そのため既存の口は使わず、建築のための内部専用の受け口 `observeInteractionInternal` を新しく作った。

| ファイル | 変更 |
|---|---|
| `src/story/economy-observer.ts` | 受け口の型 `InteractionCaptureInternal` と、変更できない写しを作る関数 |
| `src/story/engine.ts` | 年ごとの経済の計算の後で、受け口があれば写しを渡す（その年の移住 `moves`・交易 `traded`・交易路の状態と記録ID）。受け口が無ければ何もしない |
| `src/story/generated-facility-batch-internal.ts` | 本番の地形の世代の一括処理に、省略できる引数を1つ追加 |
| `src/irrigation/annual-baseline-internal.ts` | 年次処理の設定に、省略できる受け口を1つ追加（本番の地形の世代だけで使える） |
| `src/terrain/terrain-evolution-progression-internal.ts`・`terrain-production-progression-v1.ts` | 進行と選択に、省略できる引数を1つずつ追加 |

受け口に渡すのは写しだけで、v8の状態にも記録にも何も書き込まない。

### 1.3 読込時の確かめ方

交流そのものはv8の保存から計算し直せないので、v8に残っている材料との整合を確かめる。

- 交易路ごとの最後の20年の交易が、保存されている `tradeYears` と一致する
- 記録した移住に、v8自身の記録の決まり（同じ組で前の記録から10年以上空いたときに記録する）を当てはめると、保存されている `migrationYears` と一致する
- 交易路の開閉と、最後の記録IDが、保存されている交易路と一致する
- 記録した交易路の記録IDが、歴史の記録に同じ年で存在する
- 交流の記録全体のSHA-256（壊れていないかの確認。v8の `payloadHash` と同じ考え方）

建設時様式は、これまでどおり全件を計算し直して照合する。

## 3. 実装中に見つけて直したこと

- **協定の記録IDは `null` に戻ることがある**（`regional-economy.ts`）。最初は戻ったら例外にしていたが、正常な世界を拒むので、`null` への変化も記録するようにした。
- **選択が保留中の年**：v8はその年に入っているが、経済はまだ計算していない。そのため交流の記録は1年手前まで、という状態を正しいものとして扱うようにした。

## 4. 確かめ方の限界（S-Aを選んだときに想定していたもの）

- 途中の移住を1件消しても、その組の「最後に記録された年」が変わらなければ、v8に残る材料とは矛盾しない。この改竄は、ハッシュを付け直されると検出できない（テストに注記した）。
- 交易の記録も、最後の20年より前は、ハッシュでしか守られない。
- これはv8自身が、年ごとの経済の記録を読込時に計算し直さずに確かめている水準と同じである。
