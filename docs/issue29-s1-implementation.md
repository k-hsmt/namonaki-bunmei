### 1.1 v10/schemaVersion 3 を選んだ理由

D0 §3.3の初期案どおり。追加は既存`ObservationLedger`内の1フィールドで、外側packetの構成・責務は変わらない。v11の新設は保存キー・探索順・優先度削除の追加変更を伴うため、責務分離上の利点がない。

## 2. 破壊的変更と既存データへの影響

- **v10/schemaVersion 2 の保存は開けなくなる。** 起動・読込・ファイル読込では既存の「以前の版の保存です。この版では開けません。保存値はそのまま残しています。新しい文明を作ってください。」を表示し、保存キーを消去・上書きしない（既存の`OutdatedWorldSaveError`経路）。
- **再開始が必要。** 新しい文明から世界暦0年の指標履歴を持つ。旧保存の欠けた歴史を現在値・補間・逆算で埋めない。
- 本変更前に作られたv5〜v8の生成保存も、状態読取が`metrics`を必須とするため読み込めない（変更前のビルドで作った各形式の保存を本ブランチで読み、すべて拒否されることを確認）。これらは専用の「以前の版」文言ではなく既存の「この保存データを読み込めませんでした。現在の歴史と保存値はそのままです。」になる。v9は従来どおり気候以前の版として開かない。互換readerは作らない（AGENTS.md）。
- v2のレガシー移行経路（`migrateCivilization`）が作る台帳は`metrics`を持たず、読み取り契約では「記録なし（null）」。そのための補完処理は追加していない。

## 3. 既存の歴史・乱数を変えていないことの証明

既存の全状態ハッシュ固定テスト4件（seed 42/1000年、seed 1 住宅2000年、seed 1 compact 2000年、A2灌漑5 seed）は、**`observation.metrics`だけを取り除くと#29前の固定値と完全一致**することを検証する形へ変更した（固定値は変更していない）。灌漑はbase由来の`baseHash`を再計算した上で一致。凍結v5 fixtureは、世界暦0年の1行（選択待ちでない0年は検証規則上`state`の4値と同一）だけを加えて再エンコードし、除去後のハッシュが従来値と一致することを確認した。

## 4. テスト

`tests/civilization-metrics.test.mjs`（7件）：

- 0年の記録、毎年の行数＝確定年＋1、人口は既存台帳と同値、最終行＝状態。
- 選択待ち：当年の行なし・当年は読めない・直前の確定値を返す。手動／自動／JSON復元後の選択が同じ結果で1回だけ確定、過去行不変、二重確定は拒否。
- 一括600年と分割（250＋JSON往復＋350）が完全一致。
- 読み取り：負・未来・小数・NaN・文字列などはnull、未記録はnull、破損は例外。
- `commitObservation`：同年二重・年飛び・負・長さ違い・NaN・Infinity・範囲外・型違い・欠落を拒否し、拒否後の台帳は不変。
- 状態読取：欠落・null・ruleId・firstYear・未知フィールド・年欠落・未来行・空・行長・null/文字列値・範囲外・配列以外・最終行不一致・状態不一致の17形態を拒否。
- v10：選択待ち中に保存→JSON→復元で履歴一致、次の1手が同一、schemaVersion 2は`OutdatedWorldSaveError`、履歴を除いた現行保存と、過去年の1値を改変した保存は拒否（後者は保存のreplay commitmentが検出）。
